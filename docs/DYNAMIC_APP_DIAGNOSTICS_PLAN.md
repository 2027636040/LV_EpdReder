# 动态应用故障诊断实施方案

## 目标与实施范围

动态应用发生硬件异常、断言或卡死后，开发者能够使用对应构建的符号文件，将运行地址还原为函数、源码行和可恢复的调用栈。应用可能使整机停止运行；故障隔离和自动恢复不作为诊断能力的前提。

总体方案是扩展 SDK 现有模块加载、现场保存和离线分析机制。设备保存现场和必要的模块身份，电脑使用 GDB 解析，项目负责组织构建产物。运行时不建立另一套模块管理系统。

构建符号产物、设备模块身份与日志、首次断言保存修复，以及相应测试和开发说明已经实现。验证状态见 [实施 TODO](DYNAMIC_APP_DIAGNOSTICS_TODO.md)，使用方式见 [故障取证与手工定位](DYNAMIC_APP_DEBUGGING.md)。电脑侧分析工具仅保留接口和职责设计，后续再实现，不作为设备侧工作的前置条件。完整自动解析能力在电脑侧完成并通过联调后验收。

## 构建产物与精确身份

### 同一次链接生成安装文件和符号文件

主模块与私有库均采用以下构建关系：

1. 链接生成带调试信息的 `.so.nostrip`，生成并保留 GNU build-id。
2. 从该文件复制并裁剪，生成安装用 `.so`。保留加载器需要的动态符号、重定位信息和 build-id，继续遵循现有 `.hash` 处理规则。
3. 将两个文件都声明为构建输出。任一产物缺失时，构建系统按依赖补齐，不能留下新安装文件配旧符号文件。
4. 归档未裁剪文件；设备安装包不携带 DWARF 等完整调试信息。

不再编写逐节比较内容、布局和重定位的通用 ELF 等价检查器。构建依赖保证两个文件来自同一次链接，集成测试检查 build-id 保留、必要装载信息和实际加载结果。

主固件也生成并保留 GNU build-id，使日志或 dump 可以关联到相应 `main.elf`。GNU build-id 与应用版本号、平台 ABI 标识分别承担不同职责：前者选择调试符号，后两者继续用于发布和兼容性管理。安装完整性仍复用现有 `files.sha256`，不在故障路径读卡计算摘要。

没有 build-id 的旧模块仍可按原方式加载。诊断中标记身份未确认，不自动使用同名或最新符号冒充匹配结果。

### 一个清单组织调试产物

安装目录保持 `project/build_<board>/app-resources/<app-id>/`。调试产物保存在 `project/build_<board>/debug-artifacts/`，以 build-id 区分固件和模块符号文件，使用一份 `manifest.json` 建立关联。

清单包含：

- 主固件、主模块和私有库的 build-id、文件路径及摘要。
- 应用 ID、模块名、包版本与包内安装文件的对应关系。
- 板型、工具链、关键构建配置，以及工程和 SDK 的 Git 提交与 dirty 状态。
- 开发端源码路径，供后续 GDB 路径映射使用。

不拆成固件、模块、应用包三套相互嵌套的元数据协议，不在每次增量构建中自动导出完整源码。dirty 标记只说明存在未提交改动，不能用于恢复源码；需要交付可复现现场时，由显式调试包导出操作保存该次构建所需的源码或差异及未跟踪输入。

平台单独构建仍不依赖应用；单应用和批量应用构建只归档选中应用及其私有库。新构建不能覆盖不同 build-id 的既有符号；分析时始终按身份选择。

## 设备侧模块身份与地址记录

### 复用 SDK 模块对象

在 SDK 正常装载 ELF 时读取 build-id，并在模块对象的诊断字段中保留值，供日志和 dump 使用。字段随模块创建和释放，不建立另一份常驻模块数组，也不占用已有业务用途的 `user_data`。

build-id 在已有 ELF 输入仍有效时提取，不为诊断重复打开 TF 卡文件。读取 ELF note 时遵循文件长度与字段边界；旧文件没有 note 时保持原有装载行为。增加诊断字段后同步构建引用模块结构的代码，字段布局由配套 ELF 的类型信息描述，不另维护项目专有的 C/Python 镜像结构。

诊断字段按 SDK 配置控制；关闭时保持原有功能路径。新增 RAM 占用按每个实际加载模块计，在实现后用结构大小及链接结果报告，不预先保留一个与实际模块数量无关的 RAM0 历史区。

项目现有应用、存储介质、TF 卡会话和引用计数管理继续承担业务安全职责。诊断清单在电脑上关联应用 ID 与模块身份，SDK 不需要理解应用安装目录或卡会话。

### 两个日志位置

| 记录 | 输出时机 | 最小内容 |
| --- | --- | --- |
| 模块映射可用 | 重定位、缓存维护和初始化入口解析完成，调用 `module_init` 之前 | 模块名、build-id、模块对象地址、`exec_mem_space`、`mem_size`、`vstart_addr` |
| 即将释放执行内存 | `module_cleanup` 和前置资源清理完成，释放代码内存之前 | 模块对象地址、build-id 和执行基址 |

日志采用固定键名和单行结构，直接由 SDK 加载器的共用诊断函数输出。卸载行的含义是“即将释放”，不宣称该行输出时释放已经完成。实际故障发生在释放窗口内时，以同一现场的模块对象、内存和 CPU 位置判断。

初始化和清理函数执行期间，模块对象及映射一直有效。增加或减少引用不产生卸载日志；仅在实际销毁位置输出。失败路径继续使用已有加载错误日志，不增加完整加载事务状态机。

完整 dump 优先读取 SDK 对象。主机按照 RT-Thread 实际对象归属遍历全局对象及模块所属对象，使用已捕获内存范围检查地址并识别链表环。损坏对象或缺失内存只降低诊断完整性，不反过来影响设备应用加载。

只有串口日志时，按同一次启动内的记录顺序还原已观察到的映射。日志截断、缺少启动边界或地址复用关系不完整时，报告无法确认。已经卸载模块的旧记录可以帮助识别可疑旧地址，但不能单独证明发生了卸载后访问。

## 故障现场与卡死取证

### 硬件异常

继续使用 SDK 的 `saved_stack_frame`、`saved_stack_pointer`、`saved_scb_reg` 和 `error_reason`，保留现有转储格式。故障路径不额外分配内存、不等待应用锁、不调用应用代码，也不从 TF 卡补读模块身份。

不要求异常处理器遍历并打印全部模块。正常加载日志已经给出映射；转储中的 SDK 对象提供当前映射。两者都不可用时，保留原始地址并说明无法完成模块匹配。

程序计数器 PC 表示该上下文的执行位置，LR 保存返回地址，SP 指向栈。故障指令位于某个应用内，只能定位触发位置，不能据此认定该应用最先破坏了内存。

### 首次系统断言保存顺序

实施前，系统断言进入 `rt_assert_handler` 后先操作控制台和打印系统信息，最后才调用 `rt_hw_fatal_error`。这些操作再次断言时，首次现场可能尚未保存。修复此处属于有源码和故障模式依据的最小 SDK 改动。

实现时将“保存现场”与“复杂诊断输出”分离，在首次系统断言的防重入判断后、任何可能再次触发断言的诊断操作前固定上下文。保留已有保存变量、格式和停止语义；嵌套断言或硬件异常不能覆盖已经固定的首次系统断言上下文。不以提前调用整套打印和导出流程代替单纯保存。

模块线程的断言另走 `dlmodule_exit` 分支。该分支在退出前补齐断言表达式、函数和行号的诊断输出，保留原有退出行为，不把可继续运行的模块退出标记成整机终止事件，也不新增故障事件编号管理。仅有该日志而无有效寄存器和栈时，只承诺断言位置，不承诺完整调用栈。

保存函数自身的 PC 与断言源码位置分别记录和解释。实现只覆盖当前板实际使用的 GCC Cortex-M33 上下文和浮点配置；其他端口保持既有行为，不为本次功能扩展全部 CPU/编译器实现。

### 卡死

保留现有 `hang_diag`。不新增调度器中持续复制线程栈的机制，不批量修改线程、工作队列、LVGL 回调和 app_fwk 以传递应用归属。

优先暂停处理器后，一次导出当前寄存器、相关线程对象与栈内存：

- 正在运行的线程使用调试器读取的当前寄存器。
- 已被调度器切出的线程使用该转储时刻的保存 SP 和相应栈帧，按当前端口布局恢复上下文。
- 等待锁或 IPC 的线程结合已有线程状态、等待对象与可恢复栈判断。
- 关闭中断或锁住调度的卡死可能阻止监测线程运行，需要调试接口取证。

监测日志与调试器暂停时刻分别解释。旧监测 SP 不与后来变化的栈内容拼接展开。只有阶段日志而没有寄存器和栈时，报告停留阶段，不构造精确调用链。

### 采集范围

复用 SDK 已有 J-Link、AssertDump 等导出和转换能力。转储至少覆盖故障上下文、相关 SDK 模块及线程对象、线程栈；涉及动态执行代码或重定位后指令时，需要对应 PSRAM 区域。不能照搬其他平台默认只保存内部 RAM 的配置。

当前 Python 纯 UART 传输尚未登记 SF32LB57。57 的具体导出路径和 SRAM/PSRAM 覆盖范围需要用本板样本确认；必要的 UART 适配作为单独的采集任务，不混入符号解析实现，也不承诺已支持。

近期设备侧验收可以使用已有导出工具、精确符号和手工 GDB 加载。手工验证步骤只使用标准 GDB 命令，不先编写一个稍后又被 SDK 工具替代的项目分析器。

## 电脑侧分析设计

本节只确定后续实现方式，不在近期任务中实现工具代码、命令行扩展或自动报告生成。

### 扩展已有 SDK 工具

以 `SiFli-SDK/tools/sdk_py_actions/crash_dump.py` 为分析核心，延续现有 `sdk.py crash-dump` 入口，增加可选的调试清单、模块符号和上下文输入。已有单 ELF 使用方式保持兼容。

项目不另建 ELF/dump 解析器、栈展开器或独立 JSON 协议。若项目需要便捷入口，`tools/app_debug.py` 只负责定位工程默认目录并调用 SDK，不保存另一套分析状态。

后续处理顺序：

1. 按主固件 build-id 选择 ELF，保留原始 dump、日志和采集 manifest。
2. 从 dump 内 SDK 对象取得当前模块映射；同次启动的加载日志补充缺失身份或映射，并报告冲突。
3. 按模块 build-id 匹配未裁剪符号，使用调试清单关联应用及私有库。
4. 分离原始异常或断言上下文、导出时 CPU 当前上下文，以及各个已切出线程上下文。
5. 生成 GDB 附加符号命令，选用与栈内存一致的上下文展开，输出可恢复帧。
6. 扩展现有分析结果，提供人可读文本、JSON 和可复用的 GDB 命令文件。

寄存器字段继续区分 `saved_registers`、`current_registers` 和已有兼容字段，不悄悄更改含义。多个线程的上下文生成是明确的待实现工作；对单寄存器 core 执行 `thread apply all bt` 并不会自动得到 RT-Thread 全部线程。

JSON 至少说明输入身份、符号匹配状态、模块地址、上下文来源、已展开栈与缺失证据。能够使用 GDB 机器接口获取的结果优先复用其接口。工具确定性地还原事实，开发者或 AI 根据函数和源码分析原因，不新增 AI 专用诊断协议。

### 动态地址还原

当前连续 RAM 装载路径使用：

~~~text
load_bias = exec_mem_space - vstart_addr
ELF_address = runtime_address - load_bias
runtime_section_address = ELF_section_address + load_bias
~~~

`load_bias` 表示模块运行地址相对于 ELF 链接地址的偏移。GDB 的 `add-symbol-file` 使用该偏移或实际节地址，不能把整个模块基址直接当成 `.text` 地址。

保留原始地址，按 ARM Thumb 规则解释指令地址和返回地址。调用栈由 GDB 结合真实 DWARF 信息展开，不自行实现通用反汇编和返回指令猜测。栈内扫描到的代码地址只能列为候选，不冒充已经展开的调用帧。

精确符号缺失、build-id 不符、必要内存未抓取或对象损坏时，报告对应缺失并保留原始地址。旧固件身份未确认时允许显式选择符号，但输出必须说明匹配条件，而不是自动选择最新文件。

## 验证与完成标准

测试针对本项目新增的连接点，不重复验证 GDB、binutils 的通用正确性，也不因已删除的机制保留容量耗尽、历史淘汰、世代同步等测试。

| 范围 | 验证内容 | 完成条件 |
| --- | --- | --- |
| 构建关联 | 主模块和私有库一次链接、派生 strip、符号丢失后重建、同名不同构建 | 安装文件和调试文件 build-id 一致，所需加载信息保留，独立/批量构建边界不变 |
