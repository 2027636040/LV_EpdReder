# PM 接入现状与实施边界

## 状态与已有基础

系统电源管理（Power Management，PM）尚未接入当前运行流程。墨水屏完成刷新后断电、后台服务按事件等待、数据写回和可取消请求已经存在；这些能力减少无效工作，但不能证明处理器已经进入深睡或整机达到目标功耗。

[完整 PM 储备](../PM_TECHNICAL_RESERVE.md)保留 SDK 模式、唤醒、外设及产品状态的详细设计。本文件给出该设计与当前应用平台的接点。

| 当前对象 | 源码事实 | 对接要求 |
| --- | --- | --- |
| [主循环](../../src/main.c) | `lv_timer_handler()` 后将等待时间限制为最多 20 ms，服务调度还可以要求更短等待。 | 实现事件与期限驱动的 GUI 等待，才能减少周期唤醒；没有脏区不等于没有执行任务。 |
| [天气服务](../../modules/weather/weather.c) | 已按网络事件和下次同步/重试期限阻塞等待。 | 保留 30 分钟周期、5 秒重试及手动请求，接入时不再重复改造为同一种事件机制。 |

## 产品状态与持久化

产品锁屏保留页面、输入草稿、阅读会话和必要后台，锁屏画面完成后不因普通数据变化刷新。解锁恢复原页面，再消费最新快照。普通处理器空闲休眠不应变成一次 app_fwk 页面退出和重建。

产品关机使用 `OFF` 表达，原产品名称 `DeepSleep` 与 OFF 等价。关机结束正常业务，不依赖 RAM/PSRAM 保留；下次启动重新创建线程、文件句柄、网络、页面和字体对象，载入持久化数据。

运行中空闲的设计目标是 SDK `PM_SLEEP_MODE_DEEP`；OFF 的设计末端是 `HAL_PMU_EnterHibernate()`，或保持 `BSP_PM_STANDBY_SHUTDOWN` 关闭时的 `pm_shutdown()`。这些仍是接入选择，实际电源轨、RTC 持续计时与唤醒需要板上确认。

| 应用数据 | 关机准备时的职责 |
| --- | --- |
| 天气配置及有效缓存 | 复用应用记录，不为关机另发天气请求。 |
| TXT / 重排阅读位置 | TXT 保存源字节位置；重排文档保存转换版本和记录内位置，不能统一按页码恢复。 |
| 单词学习 | 同步配置、未评分卡和学习记录，依据服务保存结果决定是否完成。 |
| 微信读书 | 保存账号隔离的本地位置；需要将实际后台写入结果纳入关机完成判断。 |
| 图库及派生缓存 | 原文件不变；图像、字形和排版缓存可重建，不保存整块运行内存。 |

## 待实施流程

关机事务需要由可运行线程完成，顺序为：拒绝新业务 → 取消或完成在途工作 → 保存必要数据 → UI 绘制一次最终画面 → 等待帧传输及面板放电分别完成 → 收尾存储和外设 → 配置合法启动条件 → 进入 Hibernate。文件写入、等待线程和面板延时均发生在进入底层关中断路径之前。

普通关机保存失败时应有返回运行或重试的明确结果；低电保护不能无限等待写盘或刷新。充电唤醒只进入关机充电管理，达到开机阈值仅恢复手动开机资格，不自动启动正常应用。阈值与电源编排依赖实际板级电路。

实现先确认锁屏冻结及输入唤醒，再接 GUI 等待与保留式 DEEP，然后完成关机事务和启动判断，最后依据真实电池、充电及电源轨测量完善 LowBat/Charge。DPI 板与 LCD 载板分别核对引脚，不能将一种板的按键唤醒号直接套用到另一种板。

## 验证入口

构建检查关注最终 PM 宏、链接段及上下文依赖；软件观察使用 SDK PM 状态和唤醒记录；功耗结论来自指定供电位置、蓝牙/TF 状态及时间窗口下的电流测量。三类证据分别记录。

设备验收要覆盖静态页面、锁屏后台同步、入睡边界输入、显示完成与断电顺序、保存失败、低电和充电启动。当前没有可据以承诺续航、关机电流或唤醒时延的 PM 实测结果。
