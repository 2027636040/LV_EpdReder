# 平台演进设计

## 当前方向

平台以已有 SDK 机制为底座，通过公共服务、独立应用和参考组合向不同开发者提供入口。业务应用可独立安装和移除；组件复用不要求组件各自拥有线程，也不要求所有组件都做成动态模块。

## 演进层次

| 层次 | 当前落点 | 后续扩展条件 |
| --- | --- | --- |
| 使用成品 | 完整安装包、出厂预装、内置管理与恢复入口 | 形成经上板验证的发行组合后发布稳定固件 |
| 修改配置 | `board` 看板模板、同源几何预览 | 有真实配置需求后扩展内容类型；不另写并行页面引擎 |
| 开发应用 | 独立开发包、hello 示例、服务快照、内容交接、诊断符号 | 公共 API 出现稳定边界后再评估跨版本兼容等级 |
| 开发组件和硬件 | 项目板型、SF-PKG SD 组件、公共 HTTP/阅读/图片源码 | 第二个消费者验证独立性后拆仓并发布确定版本 |

## 组件发布

外设组件使用 SF-PKG 和现有外设仓库规范。软件组件先形成独立接口、测试和依赖声明，再选择适合的仓库。正式发布必须具有实际源码地址、维护者、许可证和不可变版本；本地缓存导出不作为远端发布的证明。

公共图片依赖归入 `modules/common/image`，HTTP 和阅读视图分别保留自己的接口。书籍格式解析目前仍有 books 所有的实现被 weread 复用；这是明确的源码依赖，后续独立为文档组件需要同步调整格式缓存、字体和部署契约，不通过复制源码拆分。

## 二进制接口演进

当前精确固件标识适合快速演进阶段。后续若需要社区应用跨固件版本运行，应先定义稳定、可版本化的接口表及能力集合，并验证 SDK、LVGL 和编译器结构体布局的影响。仅增加一个接口版本整数不能替代二进制兼容验证。

社区目录先使用可生成、可检查的静态元数据与完整目录包。在线下载、发布者认证、签名和应用隔离分别需要独立设计；没有对应实现时不在设备 UI 宣称已经提供。

## 技术储备的实施触发条件

| 储备 | 实施前所需条件 |
| --- | --- |
| PM 和关机 | 专用板外设、电源与唤醒路径确认；存储同步和重启恢复验证 |
| 离线 OTA | 重新确定可执行升级程序的位置、启动选择和升级包格式；当前无独立 OTA 程序区 |
| Wi-Fi | 确定模块、接口和 SDK 适配驱动；接入现有 network 服务 |
| 语音输入 | 音频硬件、采样链路、服务凭据和输入焦点交接确定 |
| 自动故障分析 | 在现有精确符号和模块地址证据基础上扩展 SDK 电脑端工具 |

各储备的代码现状、方案和验证入口见 [技术储备索引](TECHNICAL_RESERVES.md)。实施清单中的主机测试和编译结果不替代上述硬件条件。
