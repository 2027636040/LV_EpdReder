# 图库应用设计

## 目的与职责

`gallery.so` 提供内部存储和 TF 卡的目录浏览、PNG/JPEG 查看及重复打开缓存。当前[清单](app.json)版本为 9、数据版本为 1，不声明开机后台。图片可以位于 `/flash` 或 `/sdcard` 的普通目录，应用只读源文件，输出统一为 16 灰阶。

| 部分 | 职责 |
| --- | --- |
| [gallery_ui.c](gallery_ui.c) | UI 线程中的浏览页、查看页、列表位置、结果领取及图像绑定。 |
| [gallery_service.c](gallery_service.c) | 按需启动的受管线程，串行执行目录扫描、解码、结果发布与缓存写入。 |
| [gallery_decode.c](gallery_decode.c) | 文件适配、缓存查找和公共图片解码调用。 |
| [gallery_cache.c](gallery_cache.c) | 两个 4 位灰度缓存槽的匹配、打包、校验和替换。 |
| [公共图片组件](../common/image/raster.h) | PNG 逐行、软件 JPEG 分块及硬件 JPEG 适配，负责缩放和亮度转换。 |

## 生命周期与任务状态

根浏览页 `ONSTART` 创建八行列表及暂停的 100 ms 定时器，并调用 `gallery_start()`。`ONRESUME` 根据保存路径重新扫描；`ONPAUSE` 暂停定时器并取消该页请求；`ONSTOP` 删除定时器并请求服务停止。未打开图库时没有常驻解码任务。

浏览器保存当前目录、分页起点和选中图像。打开图片时先将路径复制到模块缓冲区，再通过框架创建查看页；查看页复制路径并按请求编号领取图片，跨页面消息不携带浏览页的借用指针。返回时取消旧请求并回到浏览页。框架拥有页面及控件树，应用拥有列表结果和图像缓冲。

文件管理器可通过已实现的[跨应用内容打开](../../docs/CONTENT_HANDLERS.md)将 `.png`、`.jpg`、`.jpeg` 文件交给图库。`app_main()` 先将请求路径复制到自有缓冲区，浏览页等待图库服务启动后再次检查存储可用性和 TF 卡会话，再创建查看页。文件交接只接受 `/flash/` 或 `/sdcard/` 下的普通文件；恢复模式、失效会话或消息容量不足时拒绝请求，不截断路径。文件扩展名声明用于发现处理者，实际编码能否解码仍由图片后端判断。

每次 `gallery_submit()` 生成新的请求编号 `serial` 并使旧请求失效。工作线程依次执行扫描或解码、发布结果、可选缓存保存，然后阻塞等待；UI 仅在等待任务时检查结果，领取后暂停定时器。取消、介质失效和线程停止均在文件读取与解码过程中检查，不把过期图片绑定到新页面。

## 图像路径与显示范围

扩展名筛选接受 `.png`、`.jpg`、`.jpeg`，不区分大小写；实际解码按文件头确定编码。图片在 620×966 区域等比居中，透明像素合成白底，缩小采用面积平均，放大采用双线性插值。缩放后的亮度舍入到 0、17、34……255，再用 RGB565 表达这 16 个等级。

| 后端 | 使用条件和工作集 |
| --- | --- |
| libpng/zlib | 普通 PNG 按行读取，Adam7 按有效源坐标累计到目标尺寸缓冲；不创建原尺寸整张 RGBA 图。 |
| TJpgDec | 基线 JPEG 逐块输出亮度，按显示需求选择解码缩小比例，再完成剩余缩放。 |
| SF32LB57 JPEGD AHB | 可随机读取的基线 YCbCr 4:2:0 JPEG 优先尝试；分配完整压缩输入和按 HAL 对齐的 YUV 输出，只读取亮度平面用于缩放。 |

硬件路径通过 SDK GPU 锁与显示共享硬件，取消、错误或超时后先结束硬件访问再释放缓冲；分配或硬件解码失败可退回软件路径。硬件整图输出随源像素数增长，软件流式路径保留用于其他采样、流输入或资源不足场景。渐进式和 CMYK JPEG 不属于当前解码范围。

普通灰阶、抖动和模式切换目标已取消；当前不保留多套效果图。EXIF 方向自动旋转和 ICC/Gamma 色彩管理尚未实现。详细后端配置见[图库说明](README.md)。

## 数据所有权与接口

[gallery.h](gallery.h) 定义 `gallery_submit()`、`gallery_take()`、`gallery_cancel_request()` 和结果释放接口。`gallery_take()` 将匹配的完成结果交给 UI；不匹配结果由服务释放。结果内的 `references` 表示真实持有者数量，UI 与缓存打包线程可同时只读同一份显示像素。

工作线程发布图片后保留自己的引用，在缓存打包结束后释放。UI 解除图片数据源、等待绘图完成并清除图像缓存引用后，再调用 `gallery_result_free()`；最后一个引用释放时回收像素。解码器内部灰度图、累加区、源文件读缓冲和坐标表由后台负责回收，不交给页面。

目录读取和文件操作在存储锁内检查可用性。应用安装卷与图片来源卷可能不同；任一相关介质失效都不能继续使用旧句柄。TF 卡移除时平台统一停止动态应用，包括内部安装的图库；清理完成后内部应用可重新运行。线程停止后平台才释放其模块引用，后台不保存 LVGL 控件指针。

## 持久化

图库没有跨启动保存的浏览位置或用户配置。目录位置只在当前页面上下文内保留；磁盘内容是可重建的图片缓存。

缓存为安装卷上的 `cache/gallery/image0.g4` 和 `image1.g4`，内部路径以 `/flash` 开头，卡内路径以 `/sdcard/.epd` 开头。源路径哈希选择槽位，同槽新图片替换旧图片。缓存按每像素 4 位保存最终灰阶值，命中后直接生成 RGB565 显示缓冲。

匹配条件包含源路径、大小、源内容 CRC 和显示尺寸，另校验缓存像素 CRC。内部文件系统没有可用的 mtime，因此命中前仍需读取源文件确认内容。缓存节省解压与缩放，不消除所有读取。缓存写入晚于结果发布，失败不影响已经生成的图片；失去源文件后，缓存也不成为可独立浏览的照片。

## 构建与部署

```powershell
. .\SiFli-SDK\export.ps1
scons -C project --board=dpi-hdk_lb57gyd7n6_epd_hcpu -j8
scons -C modules APPS=gallery -j8
```

命令在仓库根目录执行。已有兼容平台时只执行应用构建，将 `project/build_dpi-hdk_lb57gyd7n6_epd_hcpu/app-resources/gallery/` 完整复制到 TF 卡 `apps/gallery` 并通过系统安装。LCD 载板使用对应 `FIRMWARE` 参数；平台依赖与预装见[构建说明](../../docs/BUILDING.md)。

## 验证入口与演进

[test_raster.py](../common/image/tests/test_raster.py) 使用实际软件解码器检查灰阶像素、错误和资源回收；运行条件及样本参数见[图库说明](README.md)。设备侧应核对首开与缓存命中、透明/交错 PNG、不同 JPEG 路径、返回时取消及拔卡。主机软件测试不能证明 JPEGD、显示缓存同步或面板刷新正确。

文件交接已实现，其路径和存储边界及主机验证入口见[跨应用内容打开](../../docs/CONTENT_HANDLERS.md)。早期后端比较保留于[图片技术储备](../../docs/IMAGE_DISPLAY_TECHNICAL_RESERVE.md)；当前 AHB 输出与软件缩放的实现以上述源码为准，JPEGD→EPIC 直接缩放仍是独立候选。
