# 图库动态应用

图库以 `gallery.so` 安装，通过 app_fwk 管理文件浏览页和图片查看页。入口图标是安装包中的独立 EZIP 文件，桌面显示入口时不装载解码器。

## 使用

1. 使用配套固件启动设备，把构建目录 `app-resources/gallery` 完整复制到 TF 卡的 `apps/gallery`。
2. 在“设置 → 应用管理 → 应用安装”安装图库。
3. 打开图库，选择“内部存储空间”或“TF 卡”，进入文件夹后打开 PNG、JPG 或 JPEG 文件。扩展名不区分大小写，解码时按文件头识别格式。
4. 图片统一以 16 灰阶显示；返回图标返回原目录，保留列表页和选中图片。目录列表每页显示八项。

图片可以放在 `/flash` 或 `/sdcard` 下的普通目录，不要求固定的图片文件夹。图库不修改源文件。

## 图像处理

图片在 620×966 区域内等比居中显示，缩小时平均源像素，放大时对临时灰度图进行双线性插值。透明像素与白色背景合成。缩放完成后，将亮度舍入到 0、17、34……255 共 16 个等级，再编码为 RGB565 交给显示层。

解码按行批量合成亮度，预先计算横向缩放坐标，并将落到同一个目标像素的连续源像素先累加后写入缓冲。普通 PNG 只保留一行目标像素的累加值，凑齐该行需要的源行后立即生成灰度行。软件 JPEG 按横向 MCU 块带输出，使用最多 16 行的循环累加区；一条块带的所有列完成后生成完整目标行，未完成的目标行保留到下一条块带，面积平均与舍入规则不变。Adam7 仍保留显示尺寸累加区。放大时复用横向插值坐标。解码器和图像处理代码按速度优化编译。不应用 ICC/Gamma 色彩管理，JPEG 的 EXIF 方向标签暂不自动旋转。

## 解码范围与内存

PNG 使用 libpng 1.6.58 和 zlib 1.3.2 的逐行读取接口，支持 RGB、RGBA、灰度、调色板、透明色、16 位通道和 Adam7 交错格式。灰度和调色板图保持单通道，灰度透明图保留双通道，不再统一展开为 RGBA。调色板预先合成为白底亮度查表。交错图按各遍的实际源坐标累加到显示尺寸的缓冲，不创建原尺寸整图。通道为 16 位时转换为 8 位进行显示。

JPEG 在模块内独立编译 TJpgDec R0.03，基线 JPEG 按最小编码块直接输出灰度，跳过色度逆变换和 RGB 转换，并使用快速 Huffman 查表。根据显示尺寸选择 1、1/2、1/4 或 1/8 输出比例，缩小后的宽高均不得低于显示所需尺寸，再完成剩余的面积平均。1/2、1/4 路径仍执行亮度逆变换，1/8 路径直接使用块的 DC 分量，不能将输出像素减少比例等同于解码加速倍数。渐进式、CMYK 等不支持的编码显示错误提示。

可随机读取的基线 YCbCr 4:2:0 JPEG 优先使用 SF32LB57 JPEGD 的 AHB 输出模式，直接向 RAM1 写入亮度和色度平面。平台通过 `HAL_JPEGD_GetBufferSize` 和 `HAL_JPEGD_GetOutputSize` 查询工作区与输出大小，应用按实际需求动态申请，不设置 480×480 或 256 KiB 的硬件路径门槛。输入缓冲按压缩文件长度分配；输出按 HAL 的 16 像素行列对齐保存，灰度缩放只读取有效区域的亮度平面，不创建原尺寸 RGB565 中间图。硬件临时内存约为压缩文件大小、对齐后源像素数的 1.5 倍，以及 32 行工作缓冲之和。

JPEGD 与 LVGL 通过 SDK 的 GPU 锁串行使用共享硬件。解码线程以信号量等待完成；取消、硬件错误或 500 ms 超时后，在持锁状态复位解码硬件、恢复回调，再释放临时内存。分配失败或硬件解码失败时回退软件流式解码；取消或源文件读取中断则结束任务。4:4:4、4:2:2、单通道和仅支持向前读取的 JPEG 使用软件路径，保留逐块解码与内存受限时打开大图的能力。

主固件在页面绘制前注销 LVGL 的 TJPGD 解码适配器，避免其格式探测函数的 4 KiB 局部工作缓冲溢出 EPIC 线程栈。`LV_USE_TJPGD` 保持开启，图库模块仍独立编译 TJpgDec 核心，在后台完成解码后向 LVGL 提交 RGB565 图像；EZIP 和硬件 JPEG 路径保持不变。

源图由解码器检查编码和尺寸，缓冲区按实际需要申请；尺寸计算无法用目标整数类型表示或内存申请失败时结束任务并释放资源。PNG 不另设源图边长、总像素、块内存或会话累计内存上限。源文件统一通过 32 KiB、32 字节对齐的 RAM1 读缓冲访问，解码器的小块读取和跳过操作复用缓冲。

热点工作区按申请时的可用空间优先动态分配到 RAM0，单次解码的 RAM0 分配预算为 64 KiB，并在每次申请前留下至少 40 KiB 的系统堆余量；其他线程仍可继续申请，因此该余量不是全局预留区。空间不足时回退 RAM1。PNG 的 32 KiB 解压字典优先取得这部分预算。所有工作区均在解码结束或取消时释放。

| 缓冲 | 用量 |
|---|---:|
| 普通 PNG 的亮度累加 | 目标宽度 × 4 B，最高 2480 B；需要 64 位累加时加倍 |
| 软件 JPEG 的亮度累加 | 块带行数 × 目标宽度 × 4 B，最高 38.75 KiB；需要 64 位累加时加倍 |
| Adam7 的亮度累加 | 目标像素数 × 4 B，最高约 2.29 MiB；需要 64 位累加时加倍 |
| 临时灰度图 | 约 0.572 MiB |
| 一份 RGB565 显示图 | 约 1.15 MiB |
| 源图横向缩放坐标 | 解码输出宽度 × 2 B |
| PNG 应用行缓冲 | 源图宽度 × 转换后的通道数 B |
| libpng/zlib 会话分配 | 按解码器需要动态申请，无项目侧累计门槛 |
| JPEG 软件解码工作池 | 20 KiB |
| 源文件读缓冲 | 32 KiB |
| 可选的 4 位缓存打包缓冲 | 约 293 KiB，含文件头 |

这些缓冲不全程同时存在：解码结束释放累加区和源图坐标表，再生成显示图。显示图完成后立即释放临时灰度图；退出查看页时等待 GPU 读取结束再释放 RGB565 显示图。大缓冲使用共享 RAM1 堆，实际申请仍取决于其他应用占用和连续空闲块，不会将整图内存转移到 RAM0。

缩放坐标乘法使用 64 位计算；仅在一个目标像素覆盖的源像素数量可能使 32 位亮度累加溢出时，改用 64 位累加缓冲。普通图片保持原有的 32 位缓冲和逐行处理方式。

## 重复打开缓存

应用安装卷的 `cache/gallery/image0.g4` 和 `image1.g4` 是两个固定缓存槽：内部路径以 `/flash` 开头，TF 卡路径以 `/sdcard/.epd` 开头。源路径哈希选择槽位；同槽图片替换旧缓存，并非保存整个相册。最终显示结果按每像素 4 位保存，两份有效文件总计最多约 586 KiB；替换期间还可能存在临时文件和 FAT 旧文件备份。

缓存匹配源路径、文件大小、源内容 CRC 和显示尺寸，并校验缓存像素 CRC。内部 LittleFS 没有 mtime，因此命中前仍顺序读取原文件校验内容，省掉的是解压和缩放，不是所有磁盘读取。首开时复用读取过程计算 CRC；仅当解码器没有消耗文件尾部时补读剩余内容。缓存存储的是最终 16 灰阶值，命中后通过 16 项颜色表直接生成 RGB565 显示缓冲，不再创建中间的 8 位灰度图，显示像素不变，旧缓存可继续使用。

图像结果先交给 UI，随后后台线程打包、校验并通过平台文件替换接口写缓存。UI 与后台线程分别持有结果引用；缓存打包只读显示像素，用户返回或取消时，后台停止打包并释放自己的引用，最后一个引用释放后回收图像。应用存储不可用、空间不足或缓存写入失败不影响已生成图像的显示。命中缓存时不重复写入。缓存不是原文件，移除源 TF 卡后不会作为可独立浏览的照片显示。

## 生命周期与刷新

打开图库时启动受管解码线程，退出根页时请求停止；服务管理器持有模块引用，线程关闭文件、释放缓存并退出后才允许卸载。未打开图库时不启动常驻后台任务。文件读取在存储锁内检查介质状态，拔卡沿用平台的应用退出和文件系统卸载流程。

后台线程只处理文件和像素，不访问页面控件。请求编号淘汰过期结果。页面只在等待任务时检查结果，结果消费后暂停定时器；不使用加载动画、渐变或周期性重绘。完整图像完成后提交 UI，保留平台全刷周期、局刷差分和刷新后断电策略。

## 构建与验证

```powershell
. .\SiFli-SDK\export.ps1
scons -C project --board=dpi-hdk_lb57gyd7n6_epd_hcpu HANG_DIAG=1 TLS_CERT_DIAG=1 -j8
scons -C modules APPS=gallery -j8
```

首次先编译平台；已有配套固件时，只需执行应用构建命令。该命令只构建图库安装包，并检查图库模块导入符号。
新增平台接口会改变应用兼容标识，其他已安装应用也需按需重新构建配套包。普通固件下载保留内部文件系统。
批量构建和可选预装见 [平台与应用构建](../../docs/BUILDING.md)。

上板检查：两种存储读取；横竖图等比缩放和 16 灰阶；透明与交错 PNG；大 JPEG；读取中返回或拔卡；反复打开退出后检查 RAM0/RAM1 是否回收。使用同一原图分别比较首次打开与出现 `gray16 cache hit` 的再次打开；修改同路径图片内容后应重新解码。

串口的 `JPEGD hardware` 和 `JPEG gray MCU streaming, scale=1/N` 区分两条 JPEG 路径，PNG 日志说明实际通道数及是否交错。`decode` 记录格式解码、补读文件尾和灰度归一化阶段的墙上时间；其中的 `read` 累计原文件读取及存储锁等待，不是纯 CPU 时间。`RAM0 peak` 统计图库解码热点分配器的峰值，不含线程栈和模块代码。`image ready, gray16` 记录从打开源文件到 RGB565 显示缓冲准备完成的时间，不包含缓存打包、缓存写盘和面板刷新时间。

## 依赖

`third_party/libpng` 来自 [libpng v1.6.58](https://github.com/pnggroup/libpng/tree/v1.6.58)，`pnglibconf.h` 是图库的只读构建配置。
`third_party/zlib` 来自 [zlib 1.3.2](https://zlib.net/)，构建使用 `Z_PREFIX` 避免与 SDK 的 CRC 等符号冲突。依赖许可证随源码保留；未启用 LodePNG，也不替换 UI 资源的 EZIP 路径。

`third_party/tjpgd` 来自 [ChaN TJpgDec R0.03](https://elm-chan.org/fsw/tjpgd/arc/tjpgd3.zip)，配置和灰度饱和修正见该目录 README。图库与书架通过共享图片组件各自编译该副本，不修改 SDK 的 LVGL 解码器。
